# RCA — build_image failure, run 62d8c6b5-500a-4481-aa34-0728a645e582 (dev-foxy-pull)

## Outcome
Deploy failed at `build_image`. **Not fixable by a manifest edit or a pipeline retry** — this is a deployment-template ↔ application-architecture mismatch plus an unsupported database engine. Pipeline was NOT re-run (a retry would fail identically, or produce a non-functional deploy).

## The reported error is a red herring
The trigger envelope surfaced the `restore-pip-cache` tail (`CommandException: No URLs matched: gs://.../pip-cache.tar.gz`). That is a **non-fatal cache miss**. The real terminating error is in the docker build step (build log lines 481–484):

```
Step #2 - "docker-build": #52 [frontend-build 13/14] RUN ... yarn install ... && yarn build
#52 yarn run v1.22.22
#52 error Command "build" not found.
#52 ERROR: executor failed running [/bin/sh -c retry_with_backoff() ... yarn ... build]
```

## Root cause
The deployment template is **`fastapi_react_mongo_shadcn_base_image` (FARM)**, whose build:
- runs `yarn install && yarn build` in `frontend/`, expecting a CRA/Vite **React SPA** that emits static `build/`/`dist/`,
- serves that **static** output via nginx / Cloudflare R2 (`frontend_type=cloudflare`),
- provides a FastAPI backend on :8001 and a managed **MongoDB**.

The actual application (FOXY) is something completely different. Evidence from the pulled source at `/app/scratch`:

1. **It is a Next.js 16 SSR app rooted at the repo top level**, not in `frontend/`:
   `next.config.js`, `next-env.d.ts`, `tsconfig.json`, `src/`, `.next/`, root `package.json`, `database/migrations/`, `scripts/db-setup.sh`, `scripts/seed-admin.js`.

2. **`frontend/package.json` is NOT the app frontend** — it is a run-glue shim:
   ```json
   { "name": "foxy-frontend-runner", ...
     "scripts": {
       "start": "cd /app && (bash scripts/db-setup.sh || true) && exec node_modules/.bin/next start -p 3000 -H 0.0.0.0"
     } }
   ```
   There is **no `build` script** → this is the direct cause of `yarn build → Command "build" not found`. The app is launched with `next start` (SSR runtime), not built into static assets.

3. **`backend/server.py` is a thin FastAPI reverse proxy**, forwarding `/api/*` to the Next.js server on :3000. It is not a real backend and reads no env vars.

4. **The database is PostgreSQL, not MongoDB.** `scripts/db-setup.sh` starts a local cluster (`pg_ctlcluster 15 main start`), creates a `foxy` role + database, applies `database/migrations/*.sql`, and seeds an admin. `DATABASE_URL` points at Postgres.

## Why this cannot be fixed here
- **Runtime model is incompatible.** FARM serves a static SPA from Cloudflare and has no mechanism to run a long-lived `next start` SSR server. Patching the Dockerfile to skip `yarn build` would still produce no static assets and no running Next.js server.
- **Database is unsupported.** The platform provisions managed MongoDB Atlas; there is no managed PostgreSQL. The app relies on a local, ephemeral Postgres cluster booted at startup (`db-setup.sh`) — that has no persistence and is not part of the managed model.
- These are architecture/platform decisions outside a manifest fix. Doing a speculative manifest rewrite is explicitly out of scope and would not yield a working app.

## Recommended fix (owned by E1 / user)
1. **Deploy on a Next.js-capable template.** The closest platform option is `nextjs_fastapi_mongo_base_image` (Next.js SSR + FastAPI, both on Kubernetes) — this at least runs `next start`. The deployment template is fixed at job start and there is no template-switch tool in the deployer; this requires re-creating/redeploying the app under the correct template.
2. **Resolve the database dependency.** The app uses PostgreSQL with a self-hosted local cluster, which the platform does not provide as a managed service. Either (a) migrate the data layer to MongoDB (the only managed DB), or (b) point `DATABASE_URL` at an external, network-reachable managed PostgreSQL — the in-pod `pg_ctlcluster` bootstrap will not persist or scale.
3. The missing `build` script and the FARM frontend/backend shims are symptoms of the wrong template being applied to a Next.js+Postgres app — they should not be individually "fixed"; the template/data-layer decision must be made first.

## What I did NOT do
- Did not edit manifests (a fix cannot bridge SSR-vs-static or MongoDB-vs-Postgres).
- Did not call `resume_pipeline` (would fail identically or ship a broken app).
- Did not create/mutate any source files.
