# RCA — dev-foxy-pull build f92789a0 (run 11ae6fe0)

## Verdict
**Same root cause as RCA_11ae6fe0. Not a new failure.** The build dies on the FARM template's `yarn build` in `/frontend` because the `/frontend` preview shim has no `build` script. Confirmed from the full Cloud Build docker-step log (not reproduced in an eph pod — the log is unambiguous and the fault is a template/source mismatch, not a runtime-secret issue).

## Exact failing command / error
Cloud Build step #2 `docker-build`, Dockerfile stage `frontend-build` step 13/14:
```
RUN ... retry_with_backoff yarn install --prefer-offline --check-files --network-timeout 100000 && yarn build
  yarn run v1.22.22
  error Command "build" not found.
  ERROR: executor failed running [/bin/sh -c ... && yarn build]: exit code: 1
ERROR: build step 2 "gcr.io/cloud-builders/docker" failed: step exited with non-zero status: 1
```
`yarn install` succeeds (shim has no deps); `yarn build` fails immediately because `/frontend/package.json` defines no `build` script.

## Red herring to ignore
The error tail surfaced `Step #0 "restore-pip-cache": CommandException: No URLs matched: gs://.../pip-cache.tar.gz`. That is a **benign first-build cache miss** — the pipeline proceeds (`Step #1 extract-pip-cache: [PIP_CACHE] No cache found, fresh install`) and the real failure is later, in the docker-build frontend stage. Do not chase the pip-cache line.

## Architecture confirmed from the build context
- Next.js app at **repo root**: `package.json` (foxy-property-web, `next build`/`next start`), `next-env.d.ts`, `tsconfig.json`, `public/`, `app`-style source.
- `/frontend` is a **preview shim only**: `package.json` + `.env` + `yarn.lock`, no `build` script, no real app.
- `/backend/server.py` is a FastAPI reverse proxy to Next on `:3000`.
- Database is **PostgreSQL**: frontend `.env` shows `DATABASE_URL=postgresql://foxy:...@localhost:5432/foxy` and the repo ships `database/migrations/*.sql`. No MongoDB.

## What the FARM template (fastapi_react_mongo_shadcn_base_image) expects
1. **`/frontend`** — a React SPA with a working `yarn build` that emits a **static** bundle to `build/` (CRA) or `dist/` (Vite). The output is copied to `/usr/share/nginx/html` and served as static files by nginx on `:8080`.
2. **`/backend`** — a FastAPI app with `requirements.txt`, started on `:8001` (entrypoint reads `[program:backend]` from supervisord.conf). nginx proxies `/api/*` → `127.0.0.1:8001`.
3. **MongoDB** via `MONGO_URL` provisioned by the deployer. No PostgreSQL is provisioned and `localhost:5432` does not exist in the FARM runtime image.

## Can a Next.js SSR app run under FARM? No.
FARM serves a **static** frontend bundle from nginx and runs only two processes at runtime (FastAPI on 8001 + nginx on 8080). There is **no process that runs `next start`** on `:3000`, so:
- Even a successful build would leave the backend's reverse-proxy to `:3000` hitting nothing → 502 at runtime.
- Next.js 16 SSR (server components, server routes, SSR data fetching) cannot be delivered as a static export, so it can't be collapsed into FARM's static-nginx model.
- The app needs **PostgreSQL**, which FARM does not provision (it provisions MongoDB). `DATABASE_URL=localhost:5432` would fail at runtime regardless of the build.

## Code-level changes (no Docker changes) — what they can and cannot do
- **Make the BUILD pass only:** add a `build` script to `/frontend/package.json` (even a no-op, e.g. `"build": "mkdir -p build && echo ok > build/index.html"`, or wire a real CRA/Vite build). `yarn build` would then exit 0 and emit `build/`, so Cloud Build's `frontend-build` stage succeeds.
- **But this does NOT make the app work.** nginx would serve the shim's placeholder output, the real Next SSR app would never run (no `next start`), and Postgres would be absent. So a code-only FARM fix yields a green build and a non-functional deployment.

## Recommended fix (needs E1 decision — not a source patch alone)
Switch the deployment to a template that runs a live Node server for Next.js SSR alongside FastAPI — the **nextjs_fastapi_mongo_base_image** (nextjs-fastapi) family — rather than FARM. Note that even that family provisions **MongoDB, not PostgreSQL**, so the Postgres dependency (`DATABASE_URL`, `database/migrations/*.sql`) is a second, separate blocker: the app either needs an external managed Postgres (set `DATABASE_URL` as a secret to a reachable host, since no platform template provisions Postgres) or a migration to MongoDB. The template is fixed at parent-job creation and is not something this deployer agent can change.

## Bottom line for E1
Adding a `/frontend` `build` script is the only code-level change that makes the FARM build succeed, and it produces a dead deployment. The genuine fix is a template change away from FARM to a Next.js-SSR-capable template **plus** resolving the PostgreSQL requirement (external Postgres via secret, or port the data layer to MongoDB). FARM cannot host this Next.js 16 SSR + PostgreSQL app.
