## Root cause — template / architecture mismatch (not a code bug, not a manifest bug)

- The deployment job's template is **FARM** (`fastapi_react_mongo_shadcn_base_image`, `frontend_type=cloudflare`). The FARM `Dockerfile.cloudbuild` `frontend-build` stage does `COPY frontend/ /app/` then `yarn install && yarn build`, and publishes the resulting static SPA to Cloudflare R2, with a FastAPI backend on :8001 behind nginx :8080.
- The actual application is a **Next.js 16 SSR app at repo root** (`next build` / `next start` on :3000) plus a FastAPI proxy at `/backend/server.py`. The `/frontend` directory is only a **preview shim** whose `package.json` has **no `build` script** — so FARM's `yarn build` dies with `Command "build" not found`.
- FARM expects a buildable React SPA under `/frontend`; this app has none. The frontend to build is the Next.js app at root, which FARM never touches.

## What is fixable here vs what requires a new job

- **Not fixable by app code in this FARM job.** Adding a `build` script to the `/frontend` shim would only make FARM build the shim, not the real Next.js app; the FARM pipeline would still serve a static SPA via Cloudflare and run FastAPI on :8001 — it has no path to run a Next.js SSR server (`next start` on :3000). The template's alias, port, and `frontend_type=cloudflare` are structurally wrong for an SSR app.
- **Not appropriate to fix by manifest override.** Making FARM build+serve a root Next.js SSR app would mean replacing the Dockerfile, nginx.conf and entrypoint wholesale and changing the serving model away from Cloudflare-static — i.e. rebuilding a different template inside FARM. That is a re-architecture, not a diagnosed manifest patch, and is not attempted.
- **Requires a new Next.js-template job.** Re-create/publish the app under a Next.js template — `nextjs_fastapi_mongo_base_image` (Next.js SSR + a separate FastAPI service, matches the `/backend/server.py` proxy) or `nextjs_mongo_shadcn_base_image` if the FastAPI piece is dropped. Those templates run `node server.js` / `next start` on :3000 and serve SSR from Kubernetes instead of Cloudflare static.

> Note on DB: the app uses external Neon Postgres (`DATABASE_URL` / `DATABASE_URL_UNPOOLED`), not the platform Mongo. The FARM `frontend/.env` shim printed in the build log carries a placeholder `DATABASE_URL=...localhost:5432...` — that is the preview shim value, irrelevant to the real Neon connection, and the build never reached any DB step. On the new job, the real Neon URL must be set as a deployment secret and the new Neon project's tables created/migrated (migrations exist under `/database/migrations`).

## Issue 2 — Secrets save returns HTTP 400 "deployer_rejected / app not found"

- `describe_deployment_state` shows `deployment_status: failed`, **no `active_run_id`**, and all four runs (`a05af993`, `360bde67`, `62d8c6b5`, `11ae6fe0`) terminal `failed`. (The two Sep-25 runs failed even earlier, at build-context prep: `read env file backend/.env: no such file or directory`.)
- A publish has therefore **never succeeded**, so no deployed app/deployment backend record exists. The Secrets panel in Publish/Manage Publishes writes against that deployed app; with no live app the deployer rejects the call → **HTTP 400 "app not found"**.
- This is **not a secrets bug and not something else** — it is a direct consequence of the build never producing a live deployment. It unblocks only once a deployment successfully goes live (which, per Issue 1, means publishing under the correct Next.js template). After the first successful publish, saving secrets will work. (No secret values inspected or printed.)

## Bottom line
One root cause drives both symptoms: the app is Next.js SSR but the job was created on the FARM template. The build dies at `yarn build` in FARM's `frontend-build` stage, and because nothing ever deployed, the Secrets save has no app to target. Fix = re-publish on a Next.js template (`nextjs_fastapi_mongo_base_image` recommended); nothing in this FARM job's code or manifests resolves it.
